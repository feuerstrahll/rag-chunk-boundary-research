# Этап A: анализ ошибок границ

Статус: план; диагностика на уровне отдельных вопросов и oracle пока не выполнялись. Цель — определить, какие потери действительно устранимы изменением границ StructureAwareChunker.

## 1. Фиксация исходной точки

Сохранить manifest входных данных, кода, parser/normalization, канонических текстов, chunks, rankings, конфигурации и среды. Проверить уникальность и соответствие query/doc/chunk IDs, хеши, диапазоны и `chunk.text == canonical_text[start:end]`. Допустимый overlap и пропуски разделительных пробелов описать явно.

В качестве исходной точки читать исторические Markdown structure chunks/rankings. Fixed используется как вспомогательное сравнение; metadata-safe корпус второго эксперимента не подменяет исходную точку сегментации. Доступная информация о title/section metadata не означает, что эти поля подавались на embedding: точную сериализацию входов нужно проверить.

Для разработки диагностик использовать исходные train 45. Учитывать, что весь набор из 75 вопросов ранее анализировался. Не обозначать использованные данные независимым финальным тестом. Порядок доступа к дополнительной итоговой выборке определяется до настройки нового метода.

## 2. Проверка gold и сохранения evidence

Для каждой пары question/evidence проверить исходный gold text, его doc_id, способ alignment, spans и долю совпадений. Разделять точное, приблизительное и неоднозначное сопоставление. Unaligned случаи учитывать отдельным числом и исключать из соответствующих coverage-оценок с явным знаменателем; не превращать их автоматически в нулевое качество поиска.

Показывать минимум: глобальное фактическое EvidenceCoverage@5, MaxSingleChunkCoverage и достижимое покрытие gold при выборе существующих чанков с заданным k/токеновым бюджетом. MaxSingleChunkCoverage — диагностика вместимости одного чанка; низкое значение само по себе не объясняет потери top-5, поскольку несколько найденных чанков могут совместно покрывать gold.

Для длинных документов зафиксировать определение длины по tokenizer и показать распределение длин. Само наличие 1 144 документов не подтверждает, что каждый из них длиннее контекстного окна.

## 3. Разметка причин

| Причина | Необходимое наблюдение |
| --- | --- |
| Неудачная граница | Gold корректно присутствует в каноническом тексте; допустимый сдвиг/переформирование локальных границ восстанавливает его при тех же ограничениях |
| Потеря поиска | Достаточное покрытие достижимо существующими чанками, но эти чанки не попали в глобальный top-k/бюджет |
| Парсинг или alignment | Исходный gold отсутствует, повреждён либо неоднозначно сопоставлен; причина проверена в исходном Markdown |
| Удалённые доказательства | Требуемые части расположены вне допустимой локальной области; локальный сдвиг границы их не объединяет |
| Проблема эталона | Проверка показывает неполноту/неоднозначность gold либо несовпадение gold с тем, что требуется вопросом |
| Не установлено | Данных недостаточно для атрибуции |

Использовать независимые признаки или несколько меток, если причины сочетаются. Сохранять цитаты, offsets, существующие и предлагаемые границы и аргументацию. Механическое разделение gold на несколько чанков ещё не доказывает ошибку сегментации.

Отдельно проверять смысловые зависимости, например отсылку к предыдущему абзацу: даже coverage=1 не доказывает, что извлечён весь контекст для интерпретации. Для такого вывода нужна дополнительная проверяемая разметка минимально необходимого контекста; её нельзя незаметно включать в исходную EvidenceCoverage.

## 4. Диагностический oracle

Заранее определить допустимые позиции границ, максимальную длину, отношение к section boundaries, overlap, число выбранных чанков k и токеновый бюджет B.

Для одного gold evidence e ввести `c(e, S)` — покрытие его проверенного span объединением выбранных чанков S с той же обработкой альтернативных spans, что и в baseline. Oracle существующих чанков:

`O_existing(e; k, B) = max c(e, S)` по `S` из существующего индекса, `|S| <= k`, `tokens(S) <= B`.

Нужно фиксировать, что считается `tokens(S)`: стоимость фактически переданных фрагментов с повторениями либо стоимость дедуплицированного текста. Использовать ту же политику во всех сравнениях. Для одного вопроса с несколькими evidence совместная оптимизация должна использовать общий S и общий B; независимые оптимумы каждого evidence дают лишь более свободную верхнюю оценку.

Oracle изменения границ строится по тому же критерию из допустимых альтернативных сегментаций. Он верхняя оценка относительно существующего oracle только если множество кандидатов содержит исходную сегментацию и остальные ограничения совпадают. Оптимизация отдельного gold без полного корпусного ограничения на размер индекса даёт оптимистичную локальную оценку, а не достижимый результат нового индекса. Если точный максимум не вычислен, результат следует назвать эвристическим, а не строгой верхней границей.

Разрыв между oracle существующих чанков и фактическим retrieval указывает на возможную потерю поиска. Разрыв между oracle изменения границ и oracle существующих чанков характеризует потенциальный запас выбранного класса границ, с учётом описанных послаблений. Ни одна величина не гарантирует, что retriever найдёт новые чанки.

Gold используется здесь только диагностически. Spans, ответы, oracle-решения и метки финальной выборки не становятся признаками или материалом настройки CBO.

## 5. Результат этапа и дальнейшие решения

Ожидаемые новые артефакты: manifest, таблица диагностик question/evidence, отдельные ручные labels, агрегаты с явными знаменателями и отчёт с проверяемыми примерами. Сохранять также неудачные и неоднозначные случаи.

До разработки CBO проверить neighbor expansion на этапе B: тот же seed ranking, детерминированный порядок соседей, ограничение тем же документом, дедупликация overlap и фактическая токенизация. Сравнивать при одинаковом бюджете передаваемого контекста; отдельно показывать число seed chunks и стоимость дополнительных токенов. Точное правило отбора и packing замораживается до сравнения.

Переход к CBO обосновывается наблюдаемыми устранимыми boundary cases, потенциальным выигрышем, ограничениями и результатами простых альтернатив. Критерий практической значимости и допустимые вычислительные затраты задаются до подтверждающего сравнения. При слабом запасе корректный результат этапа — ограничить или пересмотреть гипотезу.

Формализация CBO, выбор DP/другого алгоритма и заявления о новизне выполняются после диагностики и анализа литературы. Для итогового сравнения заранее фиксируются основной endpoint, семейство дополнительных сравнений, парный bootstrap на одинаковых IDs и при необходимости поправка на множественные проверки; анализ текущего исторического набора остаётся исследовательским.
